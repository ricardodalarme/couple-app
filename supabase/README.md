## Schema layout

`supabase/schemas/<domain>/<kind>.sql`, one folder per domain, one concern per file. The engine is pg-delta
(`[experimental.pgdelta]`), which orders statements from their dependencies, so names are for reading.

| File | Holds |
| --- | --- |
| `types.sql` | enum types of the domain |
| `tables.sql` | tables, indexes, constraints, column additions, `updated_at` and local-date triggers |
| `security.sql` | `enable row level security`, grants and policies |
| `functions.sql` | functions with their execute grants (a larger domain splits by concern, e.g. `cards/drafting.sql`) |
| `views.sql` | views with their grants and GraphQL directives |
| `triggers.sql` | trigger functions with the triggers that call them |

Domains: `_cluster` (extensions, cron jobs), `_platform` (schemas, default privileges, shared helpers, rate limiter),
`identity`, `slips`, `cards`, `guest_links`, `notifications`, `realtime`, `home`, `content`, `plus`, `account`, `chat`,
`storage`, `couple_photos`, `pauses`, `signals`, `messages`, `questions`, `games`, `wellbeing`, `manual`, `programs`,
`rituals`, `logistics`, `dates`, `memories`, `lists`, `decisions`, `agreements`, `gifts`, `cross_cutting`, `graphql`.

### Where a new object goes

- A table, its indexes, constraints, policies, functions and triggers go in the domain that owns the table.
- A function goes with the table it mainly serves; a trigger goes with the domain of the function it runs.
- GraphQL directives on a constraint stay next to the constraint. Table, view and function descriptions and
  computed fields live in `graphql/`.
- Statements generated by a loop over tables of several domains go in `cross_cutting/`.
- A new enum value or column is added to the original definition in its domain, not as a second statement.

### Rules that keep a sync clean

- Folder load order is not fully dependency-driven: default privileges are only applied to tables created after
  them. `_platform` therefore sorts before every domain folder. Keep it that way.
- Statements that change the same object stay in one file, in order (for example `agreements` privileges follow the
  pattern grant in `cross_cutting/rls_patterns.sql`). A statement in another file that touches the same object can
  run before it and leave a different result.
- Never run `supabase db schema declarative generate` or `db pull --declarative` over this tree; they rewrite it in
  their own layout.
- After any change: `supabase db schema declarative sync` must print "No schema changes found" (or create exactly the
  migration you intend), then `supabase test db`.
- Add a value to an enum with `alter type public.<type> add value '<label>'`. Function parameters stay `text` and are
  cast inside, because pg_graphql does not expose functions with enum parameters.

## Tests layout

`supabase/tests/database/<domain>/<name>_test.sql`, using the schema domain names. A test that walks several domains with
shared fixtures lives in `cross_cutting/`. `00_setup/` holds the pgTAP and helper bootstrap and sorts first.
