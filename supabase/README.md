# Repara backend (Supabase)

- Remote project: `repara`, ref `esbhdlbhbeoiwaonsgdg`, region `sa-east-1`
- GraphQL: `https://esbhdlbhbeoiwaonsgdg.supabase.co/graphql/v1` (pg_graphql, camelCase via `inflect_names`)
- Source of truth: `supabase/schemas/` (declarative) + `supabase/migrations/` (applied in order)
- Tests: `supabase/tests/database/<domain>/*_test.sql` (pgTAP; `00_setup/000-setup-tests-hooks.sql` installs pgTAP in schema `tap` and helpers in `tests`)
- Client API lives in schema `public`; internals in `private` (never exposed). Everything is default-deny.

```bash
supabase link --project-ref esbhdlbhbeoiwaonsgdg   # one-time
supabase db reset --local                          # replay migrations + seed
supabase test db                                   # pgTAP
supabase db schema declarative sync --no-apply     # drift check: must say "No schema changes found"
supabase db push                                   # apply new migrations to the remote
```

Notes: `.work/backend/` (local only, not committed) holds the API contract and decisions.

## Schema layout

`supabase/schemas/<domain>/<kind>.sql`, one folder per domain, one concern per file. The engine is pg-delta
(`[experimental.pgdelta]`), which orders statements from their dependencies, so names are for reading.

| File | Holds |
| --- | --- |
| `types.sql` | enum types of the domain |
| `tables.sql` | tables, indexes, constraints, column additions, `updated_at` and local-date triggers |
| `security.sql` | `enable row level security`, grants and policies |
| `functions.sql` | functions with their execute grants (a larger domain splits by concern, e.g. `cards/drafting.sql`) |
| `views.sql` | views with their grants and GraphQL directives |
| `triggers.sql` | trigger functions with the triggers that call them |

Domains: `_cluster` (extensions, cron jobs), `_platform` (schemas, default privileges, shared helpers, rate limiter),
`identity`, `slips`, `cards`, `guest_links`, `notifications`, `realtime`, `home`, `content`, `plus`, `account`, `chat`,
`storage`, `couple_photos`, `pauses`, `signals`, `messages`, `questions`, `games`, `wellbeing`, `manual`, `programs`,
`rituals`, `logistics`, `dates`, `memories`, `lists`, `decisions`, `agreements`, `gifts`, `cross_cutting`, `graphql`.

### Where a new object goes

- A table, its indexes, constraints, policies, functions and triggers go in the domain that owns the table.
- A function goes with the table it mainly serves; a trigger goes with the domain of the function it runs.
- GraphQL directives on a constraint stay next to the constraint. Table, view and function descriptions and
  computed fields live in `graphql/`.
- Statements generated by a loop over tables of several domains go in `cross_cutting/`.
- A new enum value or column is added to the original definition in its domain, not as a second statement.

### Rules that keep a sync clean

- Folder load order is not fully dependency-driven: default privileges are only applied to tables created after
  them. `_platform` therefore sorts before every domain folder. Keep it that way.
- Declare each object once, in its final form: no `alter table ... add column`, `create or replace` or second
  `create` of the same object. Append a new column last, because the sync does not compare column order and a
  fresh database would otherwise differ from production.
- The one remaining ordering dependency is `agreements`: its `revoke update` follows the table-wide grant that the
  pattern block gives it, so both live in `cross_cutting/rls_patterns.sql`. A statement in another file would run
  first and leave a different result.
- Declarative files hold no data statements. Storage buckets are rows, created by migrations; `storage/` and
  `couple_photos/storage.sql` hold only the policies on `storage.objects`.
- Never run `supabase db schema declarative generate` or `db pull --declarative` over this tree; they rewrite it in
  their own layout.
- After any change: `supabase db schema declarative sync` must print "No schema changes found" (or create exactly the
  migration you intend), then `supabase test db`.
- Add a value to an enum with `alter type public.<type> add value '<label>'`. Function parameters stay `text` and are
  cast inside, because pg_graphql does not expose functions with enum parameters.

## Tests layout

`supabase/tests/database/<domain>/<name>_test.sql`, using the schema domain names. A test that walks several domains with
shared fixtures lives in `cross_cutting/`. `00_setup/` holds the pgTAP and helper bootstrap and sorts first.

**Run the suite only against the local stack.** The setup file creates the `tap` and `tests` schemas and does not roll them
back. Run against the linked project, it left pgTAP views readable by `anon` and visible in the production GraphQL schema.
If that has happened, remove them on the remote:

```sql
drop schema if exists tap cascade;
drop schema if exists tests cascade;
```

Edge Function helpers have Deno tests: `deno test --allow-env supabase/functions/_shared`.

## Edge Functions and their schedule

`pg_cron` calls `push-sender` every minute and `storage-cleanup` daily through `private.invoke_edge_function`. The helper
sends nothing until both Vault secrets exist, so the jobs are safe before setup. One-time setup per project:

1. Deploy: `supabase functions deploy push-sender storage-cleanup purchases-webhook guest places chat`.
2. Secrets: `supabase secrets set FCM_SERVICE_ACCOUNT=... REVENUECAT_WEBHOOK_AUTH=... MAPBOX_TOKEN=...` (plus the chat provider keys).
3. In the SQL editor, outside migrations, store the project URL and a dedicated secret key (`sb_secret_...`):

   ```sql
   select vault.create_secret('https://<project-ref>.supabase.co', 'project_url');
   select vault.create_secret('<secret key>', 'secret_key');
   ```

   Any role that can log in to the database can read the key from `net.http_request_queue` while a request is pending.
   Use a key created for this purpose so it can be rotated alone.

`push-sender` and `storage-cleanup` run with `verify_jwt = false` and check the secret key themselves
(`supabase/functions/_shared/auth.ts`). `chat` and `places` rely on `verify_jwt = true` and read the claims from the verified token.

## Decisions that look like findings

These show up in advisors or reviews and are intentional. Revisit them only with the reason in mind.

- **Plus-only content is readable by every signed-in user** (decision D-029): the app must list locked items by title, and the
  content is not secret. Server-enforced Plus limits are slips, cards and mascot messages. The `sensitive` flag and the
  `sensitive_tracks` consent are a UX gate the user controls, not a security boundary.
- **`app_config` is readable by `anon`** (advisor 0024): the limits and the minimum app version are read before sign-in.
- **GraphQL introspection is on** (`graphql/schema_settings.sql`): the Supabase docs recommend turning it off in production,
  but the schema snapshot is generated from the project in `.env.development`. Turning it off in production means switching
  the snapshot to the local stack, with `seed.sql` turning it back on there (the seed never runs on the remote). Row access
  does not depend on introspection.
- **Public `security definer` functions are the API** (advisors 0028 and 0029 on `authenticated`): each one starts with
  `private.require_user()` and scopes rows by the caller. `anon` can execute none of them.
- **Every table is visible to `authenticated` in the GraphQL schema** (advisor 0027): the app reads them. Rows are protected
  by RLS.
- **Tables in `private` have RLS on and no policies**: the schema is not exposed and `authenticated` has no grants, so the
  default deny is deliberate.
- **Email sign-up is enabled in `config.toml`** for the local debug sign-in only. Leaked-password protection needs the Pro plan;
  turn it on if email sign-in is ever enabled in production.
- **Realtime uses private channels.** In the dashboard, Realtime settings, turn off "Allow public access" so only authorized
  channels connect. Only a `select` policy exists on `realtime.messages`, so clients receive but cannot broadcast.
